### 二、 详细复习重点（按文档内容归纳）

#### 1. 基础概念与定义（填空/判断高发区）

请务必记住以下英文关键词及其定义，PPT中直接给出了句子，极可能考**填空**：

- **Instance（实例）**：特定时刻存储在数据库中的信息集合 4。
- **Schema（模式）**：数据库的整体设计 5。
- **Foreign Key（外键）**：一个关系模式中的**属性对应另一个关系的主键** 。
- **无损分解（Lossless Decomposition）**：分解后的自然连接能还原原关系（$\Pi_{R1}(r) \bowtie \Pi_{R2}(r) = r$） 。
- **原子性（Atomicity）**：**1NF要求属性域是原子的**，多值或复合属性不是原子的 。

#### 2. 数据库设计与SQL（大题重点，约50分）

- **ER模型设计** ：

	- **场景**：PPT给出了医院（患者、医生、测试）的案例。
	- **绘图**： 必须会画 **Entity（矩形）**、**Relationship（菱形）**、**Attribute（椭圆）**。注意**多对多（Performed-by）和一对多关系的画法**。
	- **ER转关系模式**：这是必考点。PPT展示了如何将ER图转化为表结构，特别是 **Mapping Relationship**（如 `doctor-patient` 表包含两边的主键）10101010。

- **规范化（Normalization）** ：

	- **找候选键（Candidate Keys）**：给定**函数依赖（FD），找出所有候选键。**
	- **分解**：将关系分解为 **3NF** 或 **BCNF**。
	- **3NF定义**：$\alpha \to \beta$，要么**平凡**，要么 **$\alpha$ 是超键**，要么 **$\beta - \alpha$ 中的属性包含在候选键中** 。

- **关系代数（Relational Algebra）** 13：

	- **题目**：查询为 "XYZ Bank" 工作的员工姓名和城市。
	- **写法**：熟练**使用 $\Pi$ (Project), $\sigma$ (Select), $\bowtie$ (Join)。**
	- **公式**：$\Pi_{employee-name, city} (\sigma_{company-name="XYZ"} (works \bowtie employee))$。

	**SQL语句** ：

	- **Update**：更新工资（`set salary = salary * 1.1`）。
	- **Subquery**：嵌套查询（`where employee-name in (select ...)`）。
	- **Grant**：授权操作（`grant update (salary) on works to John`）。

#### 3. DBMS内部原理与优化（计算与简答）

- **索引（Index）**：
	- **B+树**：知道 Order $n$ 的B+树，如果有 $K$ 个搜索键，树高不超过 $\log_{\lceil n/2 \rceil}(K)$（PPT写的是 $\log_2 K$，可能是简化版，需确认公式）。
	- **哈希（Hash）**：最佳情况下的块传输次数是 $b_r/b_b$（这里OCR识别可能有误，通常通过Bucket数量估算IO），理想哈希函数是均匀且随机的。
- **查询处理与优化** 1717：
	- **启发式规则（Heuristic Rules）**：这是填空题重点。
		1. **Select** 操作尽早做（Perform select operations as early as possible）。
		2. **Project** 操作尽早做 。
	- **代价估算**：Merge Join 的磁盘估算公式（音频和文档都提到了）。
	- **流水线（Pipelining）**：将元组传递给父操作，甚至在操作执行时就开始 。
	- **磁盘I/O时间**：包括 **Seek time**（寻道时间）和 **Rotational latency**（旋转延迟）。

#### 4. 事务与并发控制（Transaction & Concurrency）

- **ACID属性**：Atomicity, Consistency, Isolation, Durability 。
- **状态机**：事务执行完最后一条语句进入 **Partially committed** 状态 ；回滚后进入 **Aborted** 状态 。
- **可串行化（Serializability）**：
	- **优先图（Precedence Graph）**：如果**有环（Cycle）**，则**不是冲突可串行化的** 。
	- **判断**：调度S等价于串行调度。
- **可恢复性（Recoverable）**：如果 $T_j$ 读了 $T_i$ 写的数据**，$T_i$ 必须在 $T_j$ 之前提交**。
- **级联回滚（Cascading Rollbacks）**：可以通过 **Strict Two-Phase Locking (Strict 2PL)** 协议避免。

# 讲义四

## 大知识点

## **index**与**search key**的关系

------

T = 最底层实际存储数据的部分**（表的内容）**

### 定义回顾

- **index（索引）(不单单是一个值而已)**：数据库或存储系统中为某个或某些字段建立的**辅助数据结构**，用于加速数据查询。例如，你在某表的"a"字段上建立了索引。
- **search key（查找键/检索键）**：**用于查询的关键属性（字段值）**，通常是SQL语句中的条件字段，比如 `WHERE a=21`，此时search key就是“21”。

------

### 关系解释

1. **索引是基于search key构建的：**
	- 索引的本质是**在search key（如主键、唯一值或其他字段）上建立的**数据结构（如B+树、哈希表）。
	- 它把search key的可能取值和实际数据的位置关联起来，比如“a=21”指向对应的记录。
2. **查询时用search key访问index：**
	- 每次查询时，查询条件会变成search key（如“21”）。
	- **索引利用search key去查找定位实际数据**（通常是通过索引搜索结构跳转指针）。
3. **只有在selection condition用到search key时，索引才有效：**
	- **你只能用索引查询那些作为search key的字段**（如有“a”索引，则可查a=21，不能查b=xxx）。

------

### 图例说明（结合你的图片）

- 图中的“index scan”过程，实际上是**用search key（如a=21）在index结构上查找。**
- index（索引）**存的是search key（如[1,3,11,13,...,23,30,...]）**，每一个search key对应底层数据的位置。
- 查询时，把search key（如21）带入index结构，找到数据的位置。

## 主索引（Primary Index）和副索引（Secondary Index）

### 一、主索引（Primary Index）

- **定义**：主索引是**根据表中的主关键字（Primary Key）建立的索引**。
- 特点：
	- 通常唯一，每个表只有一个主索引。
	- 主索引的**search key**是主键字段的值。
	- 索引结构（如B+树）中的每个条目**直接指向一条基表记录的物理位置（或主文件的块）。**
	- 高效支持主键查询和数据物理排序。
	- 记录**在存储上的排列**通常与**主索引键的顺序一致**，这叫做**聚簇索引（Clustered Index）**。

------

### 二、副索引（Secondary Index）

- **定义**：**不是基于主键字段，而是表中其他字段建立的索引都叫副索引。**
- 特点：
	- 一个表可以有很多个副索引（如针对姓名、年龄等字段分别建索引）。
	- 副索引的search key是非主键字段的值。
	- 索引结构中的每**条记录指向的是主索引或主文件中对应的"主键值"（真实物理位置通常需要二次查找）。**
	- 物理排序和存储与副索引字段没有必然关系。

------

### 三、主索引与副索引的关系

1. **定位方式不同**：
	- 主索引查找时，index条目直接指向实际数据位置。
	- 副索引查找时，index条目**先得到主键，再通过主索引找到数据。**
2. **速度**：
	- 主索引通常查找速度最快（因为直接找）。
	- 副索引**多一步，通过副索引找到主键值，再通过主索引或数据文件定位数据。**
3. **应用场景**：
	- **主索引**用于主键等值查找、排序。
	- **副索引**用于非主键字段的查找或条件查询。
4. **从属关系**：
	- 副索引结构通常会存储主键值（因为**最终定位还是通过主索引/主键**）。
	- 所以副索引是“依赖于主索引或主键”的，**不能独立完成最终数据定位。**

------

### 四、举例说明

假设有表：student(id, name, age)

- 主索引建立在id字段（主键）上。
- 副索引可以在name或age字段上建立。

当用副索引name定位到"name=Tom"时：

- 副索引**查到Tom的主键id=101。**
- 再通过**主索引用id=101定位到Tom的详细数据。**

------

### 总结一句话：

- **主索引是唯一、直接定位数据的索引**，通常与物理存储顺序一致。
- **副索引是辅助、间接定位数据的索引**，查找到主键后还需通过主索引再定位到实际数据。
- 副索引依赖主索引完成最终的数据定位。

## **equality on key** 和 **equality on nonkey** 

## 1. equality on key

- **意思**：在**主键（key）列**上做**等值查询。**
- **key**通常指的是表的**主键、唯一性约束字段或索引键字段。**
- **应用**：如 `SELECT * FROM T WHERE id = 101`，这里的 **id 是主键。**
- 特点：
	- 只会有**唯一一个结果**（或者没有），不会有多个匹配行。
	- 索引查找效率最高，可以直接定位数据页。

### 例子

假如表 T 有主键字段 id。
`SELECT * FROM T WHERE id = 23`

- 这是对 key 的**等值查询**，即 **equality on key**。

------

## 2. equality on nonkey

- **意思**：在**非主键字段（nonkey）上做等值查询**。
- **nonkey**指的是**没有唯一性约束的字段，可能有多个记录值一样。**
- **应用**：如 `SELECT * FROM T WHERE age = 20`，这里 age **不是主键。**
- 特点：
	- 可能**返回多条结果**（因为不是唯一的）。
	- 索引（如副索引）可以用来加速查找，但**仍需查出所有匹配项。**

### 例子

假如表 T 有字段 name，许多人同名。
`SELECT * FROM T WHERE name = '张三'`

- 这是对非唯一字段做的等值查找，即 **equality on nonkey**。

------

### 总结对比

| 分类           | equality on key         | equality on nonkey            |
| -------------- | ----------------------- | ----------------------------- |
| 应用字段       | 主键/唯一索引字段       | 普通字段，无唯一性约束        |
| 查询结果数量   | 唯一/至多一条记录       | 可能多条记录                  |
| 使用的索引类型 | 主索引（Primary Index） | **副索引（Secondary Index）** |
| 查找效率       | 最高，直接定位          | **次高，需扫描所有匹配项**    |

# 讲义五

## 大知识点

### **并发控制**（Concurrency Control）

## 原句分析

**Concurrency Control（并发控制）确保所有可能的调度都是 conflict 或 view serializable，以及是可恢复的，最好是⽆级联的。**

------

## 核心术语解释

### 1. **Concurrency Control（并发控制）**

- 数据库**允许多个事务（Transactions）“并发”执行**，以提升系统性能。但是并发处理可能导致数据不一致、丢失等问题。
- 并发控制的目标是让**多个事务并发运行时，仍然保证数据库的正确性和一致性。**

### 2. **调度（Schedule）**

- 指数据库系统在并发处理事务时，**实际将各事务的操作（如读/写）交错执行的一个执行序列**。

### 3. **Conflict Serializable（冲突可串行化）**

- 一种**可串行化标准**。如果一个调度**能通过交换非冲突操作的顺序，最终等价于某个串行调度**（即所有事务**依次单独完成**），就叫**冲突可串行化。**
- 冲突操作：如两个事务**同时对同一数据项读/写。**

### 4. **View Serializable（视图可串行化）**

- 是比冲突可串行化**更宽松但仍保证数据一致性**的串行化标准。它要求**调度和某个串行调度在“数据视图”上是等价**的。

### 5. **可恢复调度（Recoverable Schedule）**

- 指所有事务的提交都**只在该事务读到的全部数据都已经“被相关写入者提交过”后才能进行**，否则一旦某些事务**回滚可能导致数据不一致或丢失**。

### 6. **无级联调度（Cascadeless Schedule）**

- 在更高级的要求下，设计并发控制让**一个事务只读那些已经被其他事务提交的修改**，避免在一个事务回滚时“**连锁”地导致其它依赖它的事务也要回滚（级联回滚）**。

------

## 语句的深层含义

- 并发控制的目的是：
	- 保证所有并发调度都与串行调度在结果上一致（即冲突或视图可串行化）；
	- 保证数据可以恢复（即不会因回滚丢失未提交的数据或者导致错误）；
	- 最好还能做到“无级联回滚”，提高性能和稳定性。

------

## 应用举例

- 你在数据库系统学过的**封锁协议（Locking Protocols）**如两阶段锁定(2PL)、时间戳排序等，就是实现上述目标的典型技术。

------

## 总结（课程重点）

**这句话强调：数据库系统在设计并发机制时，要确保并发执行事务的结果与某个串行方式一样（串行化），事务之间的读写依赖关系不会造成错误（可恢复），最好还能防止因为一次回滚而触发多个事务的级联回滚（无级联）。这三个要求是并发控制协议设计的目标。**

## 为什么这里commit后的事务也需要redone

![image-20251209194209188](./%E8%AF%BE%E5%86%85%E6%95%B0%E6%8D%AE%E5%BA%93%E7%B3%BB%E7%BB%9F/image-20251209194209188.png)

触及了数据库**恢复系统（Recovery System）**的核心机制——**预写日志（Write-Ahead Logging, WAL）\**和\**持久性（Durability）**。

简单来说，**“Commit”在日志中记录了(逻辑上对用户是已完成)，并不代表数据已经真正写到了硬盘的数据文件中。(物理上不一定完成)**

以下是详细的解释：

### 1. 内存与硬盘的时间差（Buffer Pool）

数据库为了性能，**不会每次修改数据都直接写硬盘**（硬盘太慢了）。

- **内存操作：** 当事务 $T_i$ 修改数据时，它首先是在**内存的缓冲区（Buffer Pool）**中**修改数据页（Page）**。此时，这个**数据页变成了“脏页”（Dirty Page）**。
- **日志先行（WAL）：** 在**事务提交时**，数据库必须保证把**日志记录（Log Record）**写入硬盘（因为日志是**顺序写，速度快**）。只有**日志落盘了，数据库才敢告诉用户“事务提交成功”**。

### 2. 崩溃发生的时机

这就产生了一个极其关键的时间窗口：

- **时刻 A：** 事务 $T_i$ 提交，`<Ti commit>` 记录成功写入硬盘的日志文件。
- **时刻 B：** 数据库崩溃（断电、进程崩溃）。
- **时刻 C（未发生）：** 内存中被 $T_i$ 修改过的“脏数据页”**本应该在稍后被刷入硬盘**的数据文件，但因为崩溃，**内存里的数据丢失了**。

### 3. 为什么需要 Redo（仅在有出现crash故障时）

当数据库重启进行恢复时，恢复管理器看到日志里有 `<Ti commit>`：

- **它知道：** 这个事务已经向**用户承诺成功**了，**必须保证它的修改存在**。
- **它不知道：** 那些**修改过的数据页到底有没有在崩溃前从内存刷到硬盘**里。

为了**绝对安全**（保证 ACID 中的 D - 持久性），恢复机制选择**无条件地重做（Redo）**该事务的操作。

- 如果数据之前已经刷盘了，重做一次也就是覆盖**写入同样的值**，结果还是对的（幂等性）。
- 如果数据之前没来得及刷盘，重做一次就把丢失的数据补回来了。

### 4. 关于图片中提到的 `<Ti abort>` 也要 Redone

你可能会疑惑，为什么 **Abort（回滚）**的事务也要 Redo？

这通常是因为在**立即修改（Immediate Modification）**策略中：

- 如果日志里有 `<Ti abort>`，说明在系统崩溃前，数据库已经**完成**了该事务的回滚操作，并且把“回滚完成”这件事记录到了日志里。
- 但是，**回滚操作修改的数据（恢复原值）也可能还在内存里，没来得及刷盘**。
- 所以，Redo 这里的 `<Ti abort>` 实际上是为了**重做“回滚”这个动作产生的数据修改**，确保回滚的结果被**持久化到硬盘上**。
- 最终的结果确实是将**旧值**写入磁盘(不是让原来的**事务的业务逻辑成功**,而是为了确保log上的**物理上也确实完成**)。

### 总结

**Commit** 只是代表**逻辑上**事务结束了并且日志已经存好了，不代表**物理上**数据块已经存好了。Redo 就是为了把那些“**逻辑上完成了**，但物理上可能丢失了”的数据**再按照log来重新写**一遍。

## 为什么通过表格得到的是这么一个优先图

![image-20251209195327510](./%E8%AF%BE%E5%86%85%E6%95%B0%E6%8D%AE%E5%BA%93%E7%B3%BB%E7%BB%9F/image-20251209195327510.png)

通过表格（调度表）得到右边优先图的逻辑非常固定，遵循**“冲突即连线”**的原则。

以下是具体的推导步骤和原理：

### 1. 核心原则：什么是“冲突”？

在画图之前，我们需要在表格中**找到所有的“冲突操作”**。两个操作被称为**冲突（Conflict）**，必须同时满足以下三个条件：

1. 属于**不同的事务**（例如 T1 和 T3）。
2. 访问**同一个数据项**（例如都访问了 Y）。
3. 至少有一个操作是**写（Write/w）**。

**连线规则：** 如果在时间顺序上，事务 Ti 的操作 Oi **发生**在事务 Tj 的操作 Oj **之前**，且两者**冲突**，则在图中画一条有向边：**Ti→Tj**。

------

### 2. 结合图片中的具体例子分析

图片中用蓝色方框和下划线特别标注了几个冲突，我们以此为例来解释右边的图是怎么画出来的：

#### **案例 A：T1→T3 的连线（看数据项 Y）**

- **在表格中：**
	1. 先看时间靠前的部分（上方）：T1 执行了 `r(Y)`（蓝色方框圈出）。
	2. 再看时间靠后的部分（下方）：T3 执行了 `w(Y)`（蓝色波浪线方框圈出）。
- **判断冲突：**
	- 不同事务（T1 和 T3）。
	- 同一数据（Y）。
	- 一读一写（`r` vs `w`），这是**读写冲突**。
- **画图结果：**
	- 因为 T1 先发生，T3 后发生，所以画一条箭头从 **T1 指向 T3**。

#### **案例 B：T1→T3 的连线（看数据项 Z）**

- **在表格中：**
	1. 上方：T1 执行了 `w(Z)`（黑色双下划线）。
	2. 下方：T3 执行了 `r(Z)`。
- **判断冲突：**
	- 这是**写读冲突**。
- **画图结果：**
	- 再次确认了从 **T1 指向 T3** 的箭头。

------

### 3. 图中其他箭头的含义（推测）

虽然手写笔记有些潦草，但我们可以根据图中的箭头反推表格中一定存在的冲突关系：

- **T1→T2（上方弧线）：** 这意味着在表格中，应该有一个数据项（比如 X 或其他），T1 先对其进行了操作（含写），T2 后对其进行了操作。 *注意：如果是图片中 T2 在最上面先读了 Y/Z，而 T1 后来写了，那箭头应该是 T2→T1。图中画的是 T1→T2，说明可能存在其他的操作顺序或者我看漏了某个 T1 先写的变量。*
- **T3→T4（下方蓝色箭头）：** 表格下方显示 T3 操作了 Z（`r(Z)`, `w(Z)`）。如果 T4（虽然只写了 `r(V)`, `r(W)`）如果在后面有对 Z 的操作，或者其实那个 `r(W)` 是 `r(Z)` 的笔误，就会构成冲突，从而产生 T3→T4 的箭头。
- **T2→T4（右侧蓝色箭头）：** 说明 T2 先操作了某个数据，T4 后操作了同一个数据且产生冲突。

### 4. 结论：为什么要画这个图？

图片下方的红色和黑色文字总结了这个图的作用：

1. **检测循环：** "一个调度是冲突可串行化的**当且仅当**它的优先图是**无环**的。"
2. **判断结果：**
	- 如果你画出来的图里有圈（比如 T1→T2→T1），那就是**死锁**或者**不可串行化**。
	- 图片右边的图中没有闭环（所有的箭头都是顺着流向走的），所以这是一个**无环图（Acyclic Graph）**。
3. **拓扑排序：** 既然无环，就可以对节点进行拓扑排序（比如 T1→T2→T4），这个顺序就是这些事务串行执行时的等价顺序。

## 那用户撤销修改是一种什么行为呢

取决于用户点击“撤销”的时间点是在**事务提交前**还是**事务提交后**。

这两种情况在数据库里是完全不同的概念：

### 情况一：事务进行中撤销（Transaction Abort / Rollback）

这是我们刚才讨论的主要场景。比如你在转账界面输完密码，正在转圈圈时，你突然点了“取消”。

1. **行为定义：** 这叫**主动中止（Explicit Abort）\**或\**回滚（Rollback）**。
2. **数据库发生了什么：**
	- 应用程序向数据库发送一个 `ROLLBACK` 指令。
	- 数据库引擎（DBMS）会把这个事务在**内存**里已经修改的“脏数据”全部改回旧值。
	- 数据库**写入一条 `<Ti abort>` 日志。**
3. **与故障恢复的关系：**
	- **如果不崩溃：** 这就是个正常的业务逻辑，数据库**改回旧值就完事了**，不需要故障恢复机制介入。
	- **如果刚撤销完就崩溃：** 恢复机制启动，看到 `<Ti abort>`，就会执行我们刚才说的 **Redo**（重做回滚），确保硬盘上也是旧值。

------

### 情况二：事务提交后撤销（Compensating Transaction）

这是最容易混淆的。比如你昨天转账成功了（Commit了），今天你想“撤销”这笔转账。

1. **行为定义：** 这在数据库里**不叫** Abort，也不叫 Rollback。这叫**补偿事务（Compensating Transaction）**。
2. **为什么不能 Rollback？**
	- 根据 ACID 中的 **D（持久性）**，一旦事务 Commit，数据就**永久生效了**。数据库**绝对不允许**去**回滚一个已经 Commit 的事务**，否则**历史就被篡改了**。
3. **数据库发生了什么：**
	- 你的“撤销”操作实际上是开启了一个**新的事务（New Transaction）**。
	- 如果原事务是 `A = A - 100`。
	- **新事务（补偿事务）**就是执行 `A = A + 100`。
	- 这个新事务同样需要**经历 Start -> Modify -> Commit** 的全过程。

### 总结

你问的“用户撤销修改”，通常指第一种情况：

- **它的本质是：** 用户主动告诉数据库“我不玩了”。
- **数据库的动作：** 执行回滚（Rollback）。
- **结果：** 这一瞬间，它和程序出错导致的“被动中止”在处理机制上是一模一样的，最终都会产生一条 `<Ti abort>` 日志。
