# TIPS:

# 《操作系统》课程概述

操作系统是一个典型的 “system”——它完成对计算机硬件系统的抽象，为应用程序提供运行的支持。我们的课程从三个视角观察操作系统：

- 从应用程序的视角看，操作系统**定义了一系列的对象 (进程/线程、地址空间、文件、设备……) 和操纵它们的 API (系统调用)**。**这组强大的 API** 把一台计算机的硬件资源分享给操作系统中的所有应用程序。我们看到的一切程序，不限于浏览器、游戏，甚至还包括容器、虚拟机、调试器、游戏外挂，都是在系统调用 API 上实现的。
- 从硬件的视角看，操作系统是**一个拥有访问全部硬件功能的程序 (操作系统就是个 C 程序，不用怕)**。硬件会帮助操作系统**完成最初的初始化和加载**，之后，**操作系统加载完第一个程序后，从此作为 “中断处理程序” 在后台管理整个计算机系统**。
- 从数学的视角看，一切计算机系统都是如同 “1 + 1 = 2” 一样 “well-defined” 的数学对象，这包括机器、程序，当然也包括操作系统。计算机系统的行为是可以用数学函数 (当然，也可以用代码) 表示的。

## 课程组织

我们希望为同学们呈现一门编程课，每一节课都带着一个明确的，希望 “实现一点什么” 的目标，每节课都学会一类新的软件系统的实现原理，从而建立对 “操作系统是什么” 的感性认识：课堂以 “应用视角的操作系统” 为主，讲解操作系统中的对象和 API，但特别侧重 “我们能用这些机制做什么”，例如在 Linux 中复刻三类经典游戏外挂：金山游侠、按键精灵、变速齿轮，并用它们修改真正的游戏；我们也会构建操作系统的可执行模型，并用形式化方法 “暴力枚举” 操作系统上程序的所有可能行为以更好地理解操作系统 ([USENIX ATC'23 Paper](https://www.usenix.org/conference/atc23/presentation/jiang-yanyan))。

# 2. 应用视角的操作系统

## 2.1 操作系统上的程序

“状态机” 是拥有**严格数学定义**的对象。这意味着你可以把定义写出来，并且用**数学严格**的方法理解它 —— 形式化方法

### 状态

- [StackFrame, StackFrame, ...] + 全局变量

### 初始状态

- 仅有一个 **StackFrame(main, argc, argv, PC=0)**
- 全局变量全部为初始值

### 状态迁移

- 执行 frames[-1].PC 处的简单语句

操作系统最大的职责就是让我们**在编程时感受不到操作系统的存在**

实际上，C 标准中 `return f(n - 1) + f(n - 2);` 甚至不保证从左到右的调用顺序。(但现代编译器为了防止产生难以理解的执行，**通常按照自然顺序调用**、不做激进优化。)

- 序是从 _start 开始执行的

```
void _start() {    // ... } 
```

## 2.2 操作系统上的最小程序

### 程序自己是不能 “停下来” 的

- **指令集里没有一条关闭计算机的指令**，那么操作系统是如何在关闭所有软件后，切断计算机的电源的？

### 只能借助**操作系统**

```
movq $SYS_exit,  %rax   # exit(
movq $1,         %rdi   #   status=1
syscall                 # );

```

- 把 “**系统调用**” 的参数放到寄存器中
- 执行 syscall，**操作系统接管程序**
	- 操作系统可以**任意改变程序状态 (甚至终止程序)**

### (二进制) 程序 = 状态机

### 状态

- gdb 内可见的内存和寄存器

### 初始状态

- **由 ABI 规定** (例如有一个合法的 %rsp)

### 状态迁移

- 执行一条指令
	- 我们花了一整个《计算机系统基础》解释这件事
	- **gdb 可以单步观察状态机的执行**
- **syscall 指令**: 将**状态机 “完全交给” 操作系统** (上帝 & 祈祷)

## QA

### **我即便写一个空的 main()，链接后依然生成了很大的代码。怎么才能实现最小的 C 程序呢？**

要实现最小的 C 程序，可以采取以下步骤：

1. **使用最小的运行时库**：**避免链接标准库，使用 `-nostdlib` 编译选项。**
2. **手动定义入口点**：**使用 `_start` 而不是 `main`，直接调用系统调用退出程序**。
3. **优化编译选项**：使用 `-Os` 或 `-O3` 进行优化，并**去除调试信息。**

示例代码：

```c
void _start() {
    __asm__("mov $60, %eax\n"  // syscall: exit
            "xor %edi, %edi\n" // status: 0
            "syscall");
}
```

编译命令：

```bash
gcc -nostdlib -Os -o minimal minimal.c
```

这样可以生成一个非常小的可执行文件。

(jyy: 他**默认了 x86_64，而且忘记了 -static 可以更小**；但这已经非常好了。实际上，我们可以继续补充要求，让他写出能够在不同系统上可移植的代码。于是 DeepSeek 正确给出了 `syscall(SYS_exit, 0);` 的方案，但没能一次给出正确的编译选项——但在你告诉他具体错误以后，就正确给出了 **-nostartfiles** 的选项。)

操作系统就是程序的上帝，通过想好想让上帝做什么 (**根据 ABI 设置好寄存器的值**)，然后开始祈祷 (**执行系统调用对应的指令**)，然后上帝会立即显灵，完成这个任务。

## 2.3 操作系统上的应用程序

### 可执行文件是操作系统中的对象

### **任何程序 = minimal.S = 状态机**

- 总是从被操作系统加载开始
	- 通过另一个进程执行 execve 设置为初始状态
- 经历状态机执行 (计算 + **syscalls**)
	- 进程管理：fork, execve, exit, ...
	- 文件/设备管理：open, close, read, write, ...
	- 存储管理：mmap, brk, ...
- 最终调用 _exit (exit_group) 退出

**strace** (system call trace) 是《操作系统》课程中一个非常重要的命令行工具，帮助我们 “观测” 应用程序和操作系统的边界。实际上，任何程序的执行就是状态机在计算机上的运行，因此 “用合适的方式观测状态机执行” 就是我们理解程序的根本方法。**调试器、trace、profiler 提供了不同侧面的理解手段**，这三个工具将会在课程中反复出现。

## QA

### `fff.out` 和 `fff`

从操作系统的底层逻辑来看，**`fff.out` 和 `fff` 之间几乎没有任何本质区别。**

这与 Windows 有着巨大的差异。**在 Windows 中，扩展名（如 `.exe`, `.txt`）决定了文件如何被打开；而在 Linux 中，文件名仅仅是一个字符串标签。**

以下是它们之间具体的异同点对比：

### 1. 相同点：内核眼中的它们

对于 Linux 内核来说，这两个文件都只是磁盘上的 **Inode（索引节点）**。

- **执行能力：** 一个文件能否运行，不取决于它叫不叫 `.out`，而取决于它是否具有 **可执行权限（x）**。你可以通过 `chmod +x fff` 让没有后缀的文件运行。
- **类型识别：** 正如我之前提到的，Linux **使用 `file` 命令读取文件的“魔数”（Magic Number）来识别类型**，而不是看后缀。

------

### 2. 不同点：人为约定与工具习惯

虽然系统不在乎，但**人和编译器**在乎。

| **特性**     | **fff.out**                                                  | **fff (纯名字)**                                             |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **默认生成** | GCC 编译器的默认输出文件名通常是 `a.out`。程序员常加 `.out` 来表示这是一个“输出文件”。 | 现代开发中，通常使用 `-o` 参数指定一个简洁的名字，如 `gcc main.c -o fff`。 |
| **可读性**   | 一眼就能看出这可能是一个编译后的二进制结果，或者某种导出的数据。 | 看起来更像是一个系统命令（如 `ls`, `cd`, `grep` 都没有后缀）。 |
| **Tab 补全** | 在终端输入 `./fff` 后按 Tab，如果两个都在，系统会让你选。    | 如果目录下只有它，Tab 键会瞬间补全。                         |

------

### 3. 为什么你经常看到 `.out`？

这其实是一个**历史包袱**。

- 在早期的 UNIX 系统中，汇编器输出的可执行文件默认命名为 `a.out`（代表 **a**ssembler **out**put）。
- 尽管现在的 Linux 使用的是更高级的 **ELF** 格式，但 **GCC 依然保留了默认输出 `a.out` 的传统。**
- 很多学生或开发者在练习时，习惯性地给输出文件加上 `.out` 后缀，以便在充满 `.c` 或 `.h` 源码的文件夹里快速分辨出哪个是编译好的程序。

### 4. 如何验证它们？

你可以做这个小实验：

1. 把一个可执行程序 `fff.out` 重命名为 `fff`：`mv fff.out fff`。
2. 尝试运行它：`./fff`。
3. 它依然会完美运行。

**一句话总结：**

在 Linux 中，后缀名是写给**人**看的（为了方便分类），而文件权限和内部数据头是写给**系统**看的。

## 2.4 总结

**Take-away Messages**: Everything (高级语言代码、机器代码) 都是状态机；而编译器实现了两种状态机之间的翻译。无论何种状态机，在没有操作系统时，它们只能做纯粹的计算，甚至都不能把结果传递到程序之外——而程序与操作系统沟通的唯一桥梁是系统调用 (例如 x86-64 的 syscall 指令)。如此重要的桥梁，操作系统中自然也有工具：strace 可以查看程序运行过程中的系统调用序列。



# 3. 硬件视角的操作系统

## 进程与程序之间有什么区别

### 核心区别对照表

| **特性**     | **程序 (Program)**                   | **进程 (Process)**             |
| ------------ | ------------------------------------ | ------------------------------ |
| **定义**     | 磁盘上的**可执行文件（如 `a.out`）** | 正在运行的文件实例             |
| **本质**     | **静态**的指令集合（代码）           | **动态**的执行过程（状态）     |
| **存在位置** | 存储在硬盘上                         | 加载**在内存中**               |
| **生命周期** | 永久存在（除非你删除它）             | 临时存在（运行结束即销毁）     |
| **资源占用** | 仅占用磁盘空间                       | **占用 CPU、内存、I/O 设备等** |

### 深度理解（操作系统的视角）

当你双击一个程序或在终端输入 `./fff` 时，操作系统会完成从“程序”到“进程”的华丽转变：

1. **分配内存：** 为代码、数据、堆（Heap）和栈（Stack）**开辟空间**。
2. **建立 PCB：** 操作系统会创建一个**进程控制块 (Process Control Block)**。这是进程的**“身份证”，记录了进程的 PID、优先级、寄存器状态等。**
3. **开始执行：** CPU 的**程序计数器（PC）指向程序的第一条指令，进程正式“活”了**过来。

### 一个有趣的现象

**一个程序可以对应多个进程。** 比如你同时打开了三个 Chrome 浏览器窗口，磁盘上**只有一个 `chrome.exe` 程序**，但你的**任务管理器里会有三个（或更多）互不干扰的进程。**

## 3.1 硬件视角的操作系统

### RISC-V：百花齐放，百家争鸣

- 初始 PC 无规定；寄存器**除了 x0 全部 undefined**
- 少数 CSR 有规定 (例如 interrupt disabled)
	- 设计原则：**省电路**
	- 软件能做的，硬件绝对不管

### 硬件**根本不知道有没有操作系统**

### 计算机系统中的**抽象**

- 下层不需要知道上面怎么用，只管 “无情地提供服务”
	- **系统调用支撑应用**程序
	- **指令集支撑高级语言程序**

### 1. 状态

- 内存、寄存器的数值

### 2. 初始状态

- 由系统设计者规定 **(CPU Reset)**

### 3. 状态迁移

- 从 PC 取指令执行

### 寄存器、内存

```c
struct CPUState {
    uint32_t regs[32], csrs[CSR_COUNT];
    uint8_t *mem;
    uint32_t mem_offset, mem_size;
};
```

### 还有外部世界的态

- 设备上的寄存器 (memory-mapped I/O 可以访问)
- Interrupt/Reset Line
- 客观存在，但计算机系统不能直接访问
	- 类比：**进程只能通过 syscall 访问进程外**的信息

### **操作系统就是一个普通的 (二进制) 程序**

- 接管了中断、I/O、……
	- 应用程序不能直接访问
- 把应用程序 “放” 到 CPU 上运行一会
	- 中断后，操作系统又开始执行
	- (操作系统启动后，操作系统就变成了**一个中断处理程序**)

## 3.2 固件：硬件和操作系统之间的桥梁

### CPU = 无情执行指令的机器

- 从 CPU Reset 开始执行
	- **从 Mem[PC] 取**指令
	- 译码、执行，如此往复
- 这里必须得是合法的代码
	- 那到底执行了什么代码呢？
	- 代码是谁放在这里的呢？

### 答案：系统厂商的代码

- 把**一个特殊的存储器 memory-map 到 CPU Reset 后**的代码
	- 这段代码 **“出生” 就有机器完整的控制权**

### “固件”

- 厂商 **“固定” 在计算机系统里的代码**
	- 早期：固件是 **ROM**
	- 想升级？换芯片！(今天可以直接升级固件了)

### Firmware 的功能

- 运行程序前的**计算机系统配置**
	- CPU 电压、内存时序、接口开关……
	- (这些配置要生效可能需要重启计算机)
- 不严格地说，**加载操作系统**
	- QEMU：可以绕过 Firmware 直接加载操作系统 ([Manual](https://www.qemu.org/docs/master/system/invocation.html#hxtool-8))

### 一个小 “操作系统”

- CPU Reset 后初始化硬件；对接操作系统 Boot Loader

### Legacy BIOS (Basic I/O System)

- IBM PC 所有设备/BIOS 中断是有 specification 的
	- 16-bit DOS 时代 BIOS 常驻内存，提供 I/O 等功能
- 成就了百花齐放的 “兼容机” 时代
	- [AMI](https://www.ami.com/bios-uefi-utilities/) 和 [Phoenix BIOS](https://www.phoenix.com/device-firmware/), 等都活到了今天！

### [UEFI (Unified Extensible Firmware Interface)](https://www.zhihu.com/question/21672895)

- 提供更丰富的支持 (例如设备驱动程序)：指纹锁、山寨网卡上的 PXE 网络启动、USB 蓝牙转接器连接的蓝牙键盘…

### 只允许写入**信任**的固件更新

- 数字签名机制
	- 公钥加密 (Diffie-Hellman/RSA)
	- 感谢今天的 SSL/TLS (HTTPS)！
- [Intel Boot Guard 私钥泄露](https://www.binarly.io/blog/leaked-intel-boot-guard-keys-what-happened-how-does-it-affect-the-software-supply-chain)

## 3.3 加载操作系统

**OpenSBI**: 一个开源的 RISC-V 引导固件，用于管理 RISC-V 平台的启动过程。它实现了 SBI（Supervisor Binary Interface）规范，为操作系统提供了硬件抽象层，简化了系统启动和硬件管理。OpenSBI 支持多种 RISC-V 处理器和平台，广泛用于嵌入式系统和开发板。

## 3.4 总结

**Take-away Messages**: 计算机系统是严格的数学对象：没有魔法；系统的一切行为都是可观测、可理解的。**处理器是无情执行指令的机器，其 Reset 后的行为也被明确规定。Reset 后，Firmware 开始运行，随后加载操作系统。**厂商逐渐形成了 Firmware Specification 的共识（如 IBM PC “兼容机”、UEFI 等）。为支持工业级软件，这一过程相当复杂，即便是 “最简单” 的 OpenSBI 也包含大量代码。但有了 AI，你无需再为此担忧！

# 4. 数学视角的操作系统

### UNIX 系统的基本模型

- 进程
- 系统调用
- 上下文切换
- 调度

### 操作系统是**最早的实用并发**程序

- 每个进程 (程序) 都是顺序状态机
	- 但**发生中断/系统调用**以后，操作系统代码**直接执行**
	- 如果**有多个处理器 (或者允许此时切换到另一个程序执行)**，就有了**并发**

把**待运行的程序 (hello.py, proc.py 等) 想象成状态机**、**操作系统想象成状态机的管理者**，就不难理解操作系统是什么了。

## 4.3 状态机模型与模型检查器

### 状态

- **多个 “应用程序” 状态机**
	- 当然，可以是模型

### 初始状态

- **仅有一个 “main”** 状态机
	- 这个状态机**处于初始状态**

### 迁移

- **选择一个状态机执行一步**
	- 就像我们在操作系统模型上看到的那样

### **调度**：状态机的选择不确定

- 多处理器的 **“选择” 是无法控制的**
- **操作系统可以主动随机选择**状态机执行一步

### **I/O**：系统外的输入不确定

- read 返回的结果也有两种可能性

### 这样程序的执行就不是 “一条线” 了

- 从初始状态出发，可能**有多个可能的 “下一个状态”**

### 程序定义了状态机 G(V,E)

- 加上一个**起点 v0**
- 再加上**F⊆V是 “坏” (faulty)** 的状态
	- **程序正确** ≡≡ 不存在从 v0 到 v∈F的路径

### 需要找一个 **tractable** 的问题

- F⊆V+暴力枚举显然太 trivial 了
	- 我们有更好的方式表达规约 (temporal logic)
	- G(A→FB)
		- “如果 A 发生，则最终 B 会发生”
		- 哦！你需要构建一个好的逻辑系统
		- 提出一些有趣的检查算法

### 在软件系统里又是 **useful** 的

- 要走很多弯路，而且今天 temporal logic 也没落了
- 但 Verification 没有死，而且在 AI 时代肯定会走得更远

| 模块       | 系统调用       | 行为                               |
| ---------- | -------------- | ---------------------------------- |
| 基础       | **choose(xs)** | 返回一个 xs 中的随机的选择         |
| 基础       | **write(s)**   | 向调试终端输出字符串 s             |
| 基础       | **sched()**    | **切换到随机的线程/进程执行**      |
| 虚拟化     | fork()         | 创建**当前状态机的完整复制**       |
| **并发**   | **spawn(fn)**  | **创建从 fn 开始执行的线程**       |
| 持久化     | bread(k)       | 读取虚拟设磁盘块 k 的数据          |
| 持久化     | bwrite(k, v)   | 向虚拟磁盘块 k 写入数据 v          |
| **持久化** | **sync()**     | **将所有向虚拟磁盘的数据写入落盘** |
| **持久化** | **crash()**    | **模拟系统崩溃**                   |

**操作系统模型和检查器**：我们可以把 “状态机的管理者” 这个思想在 Python 世界中构造出来：我们用 Python 的函数来**声明状态机，并且实现状态空间的遍历**。所有的实现都是 “最简” 的——但它真的能用来澄清 Three Easy Pieces 里的概念：**Concurrency, Virtualization, 和 Persistence**。

## 4.4 总结

**Take-away Messages**: 程序就是状态机；状态机可以用程序表示。因此：我们可以用更 “简单” 的方式 (例如 Python) 描述状态机、建模操作系统上的应用，并且实现操作系统的可执行模型。而**一旦把操作系统、应用程序当做 “数学对象” 处理，那么我们图论、数理逻辑中的工具就能被应用于处理程序，甚至可以用图遍历的方法证明程序的正确性。**

## QA

### **我发现随着进程的创建，进程的 pid 是递增的；而 pid 是有限的 (32-bit 整数)，这是否意味着会循环导致 pid 重用？**

是的，您的观察是正确的。进程 ID (PID) 确实是有限的资源，通常是 32 位整数，理论上最大值为 2^32-1（约42亿）。随着进程不断创建，PID 会递增，**当达到系统设定的最大值后，系统会循环并重新分配较小的、已经释放的 PID。**

关于 PID 重用的几个重要点：

1. **PID 范围**：
	- 在大多数 Linux 系统中，**PID 的默认范围是从 1 到 32767（/proc/sys/kernel/pid_max）**
	- 在较新的 Linux 内核中，这个上限可以配置到 2^22（约400万）
	- 在 64 位系统上，理论上限可以更高
2. **PID 分配机制**：
	- 系统会**维护一个 PID 位图或类似的数据结构**来跟踪已使用和可用的 PID
	- 新进程创建时，内核会分配下一个可用的 PID
	- 当 PID 达到最大值后，系统会从较小的值开始重新搜索可用的 PID
3. **PID 重用策略**：
	- 系统**不会立即重用**刚刚释放的 PID，通常**会有一个"冷却期"**
	- 这是为了**避免将新进程的 PID 分配给可能仍被其他进程引用的已终止进程**
4. **PID 重用的潜在问题**：
	- 安全隐患：如果一个进程**正在引用另一个已终止的进程**，而该 PID 被重用，可能导致权限问题
	- 竞态条件：在多线程或多进程环境中，PID 重用可能导致意外行为
5. **PID 命名空间**：
	- 现代 Linux 内核支持 **PID 命名空间**，允许在容器或虚拟化环境中隔离 PID 空间
	- 这意味着**不同命名空间中的进程可以使用相同的 PID 而不会冲突**

总结来说，是的，PID 确实会循环重用，这是操作系统设计的必然结果，因为 PID 是有限资源。操作系统通过各种机制（如延迟重用、PID 命名空间等）来减轻 PID 重用可能带来的问题。

## 创建状态机

```

```

- 做一份状态机**完整的复制** (内存、寄存器**现场**,所以也相当于从这行开始继续进行,但是**`fork()` 的返回值不同**)

	- Caveat: 进程在操作系统里也有状态: ppid, 文件, 信号, ...
		- **小心这些状态的复制行为**
	- 复制失败返回 -1
		- errno 会返回错误原因 (man fork)

### 如何区分两个状态机？

- **新创建进程返回 0**
- **执行 fork 的进程返回子进程的进程号**——“父子关系”

## 进程树

### 进程的创建关系形成了进程树

A→B→C，如果 B终止了……C 的 ppid 是什么？

- 看似简单：我们 “往上提” 一层就行
- 实际复杂：
	- 子进程**结束会通知父进程**

	- “往上提” 就发错人了

### 示例程序

- 1 变 2, 2 变 4, 第 k 层有 2^(k−1) 个进程
- 很快资源就消耗光了
	- 曾经会使系统彻底卡死，但现在 Linux 有 OOM 保护

### 阅读程序，写出运行结果

```c
pid_t x = fork(); 
pid_t y = fork(); 
printf("%d %d\n", x, y); 
```

会打印 **4 行** 输出。

### 核心结论

每执行一次 `fork()`，当前的进程就会“分裂”成两个（父进程和子进程）。

- 第 1 行 `fork()` 后：产生 **2** 个进程。
- 第 2 行 `fork()` 后：这 2 个进程各自再分裂，总共产生 **4** 个进程。
- 最终 `printf`：这 4 个进程都会执行打印语句。

------

### 输出内容精简解释

在 `fork()` 的返回值中：

- **父进程**：收到的是子进程的 **PID**（一个大于 0 的数字）。
- **子进程**：收到的是 **0**。

假设第一个子进程 PID 是 101，第二个是 102，输出看起来大概是这样的（**顺序可能随机**）：

1. `101 102` （**原祖父进程**：两个 fork **都成功返回了子 PID**）
2. `101 0  ` （第一个子进程：它**在第二个 fork** 时**产生了孙子，返回 0**）
3. `0   103` （第二个子进程：它**由第一个 fork 产生**，在**第二个 fork 时产生了子进程**）
4. `0   0  ` （孙子进程：两个 fork 对它来说都是由父进程产生的）

------

### 内存视角

你可以把 `fork()` 想象成**细胞分裂**。

- 第一次分裂后，两个进程的代码**指针都停在第 2 行**。
- 第二次分裂后，四个进程的代码**指针都停在第 3 行**。
- **关键点**：由于每个**进程拥有独立的内存空间**，它们**各自持有的变量 `x` 和 `y` 的值各不相同。**

### 创建了几个状态机？

**总共创建并运行了 4 个独立的状态机。**

在计算机科学中，一个“进程”本质上就是一个**执行中的状态机**。它的状态由以下要素决定：

- **寄存器状态**（如程序计数器 $PC$，决定**下一条指令在哪**）。
- **内存状态**（如变量 `x` 和 `y` 的值）。
- **内核对象**（如打开的**文件、PID 等）**。

------

### 状态机的分裂过程

#### 1. 初始状态 (M1)

- **代码位置**：停在 `pid_t x = fork();` 之前。
- **变量**：`x` 未定义, `y` 未定义。

#### 2. 第一次分裂 (M1 $\rightarrow$ M1, M2)

执行完第一行 `fork()` 后，原有的状态机 M1 产生了一个镜像副本 M2。

- **M1 (父)**：执行流继续，变量 `x` 被填入子进程的 PID（如 101）。
- **M2 (子)**：执行流**也从同一位置继续，但变量 `x` 被填入 `0`。**
- **此时**：内存中有 2 个状态机，它们都正准备执行 `pid_t y = fork();`。

#### 3. 第二次分裂 (M1, M2 $\rightarrow$ M1, M3, M2, M4)

现在，这 2 个状态机各自执行自己的 `fork()`，再次进行镜像复制：

- **M1** 分裂出 **M3**：M1 的 `y` 拿到 M3 的 PID，M3 的 `y` 拿到 `0`。
- **M2** 分裂出 **M4**：M2 的 `y` 拿到 M4 的 PID，M4 的 `y` 拿到 `0`。

------

### 最终的 4 个状态快照

当它们走到 `printf` 时，这 4 个状态机的内部数据如下：

| **状态机编号** | **身份**      | **变量 x 的值** | **变量 y 的值** |
| -------------- | ------------- | --------------- | --------------- |
| **M1**         | 祖父进程      | 子进程1的 PID   | 子进程2的 PID   |
| **M3**         | **M1 的次子** | 子进程1的 PID   | **0**           |
| **M2**         | 子进程1       | **0**           | 孙子进程的 PID  |
| **M4**         | 孙子进程      | **0**           | **0**           |

### 关键点总结

- **代码（静态）**：只有一套。
- **状态（动态）**：有 4 套独立的寄存器和内存空间。
- **非确定性**：虽然创建了 4 个状态机，但操作系统调度它们的顺序是不可预测的。所以你每次运行，`printf` 打印这 4 行的**先后顺序**可能会发生变化。

## 如何输出

```c
    for (int i = 0; i < 2; i++)
    {
        fork();
        printf("Hello\n");
    }
```

正常6个,但是 ./a | cat有8个

**标准 I/O 缓冲区（Standard I/O Buffer）的继承。**

你观察到的 8 个 `Hello`，正是因为你在命令后面加了 `| cat`（管道）。

------

### 1. 背后发生了什么？（行缓冲 vs. 全缓冲）

在 Linux 中，C 语言的 `printf` 并不是直接把字符发给内核，而是先存在一个**缓冲区**里。这个缓冲区的刷新策略取决于输出去向：

- **输出到终端（互动模式）：** 采用 **行缓冲 (Line Buffered)**。遇到 `\n` 就会**立刻把缓冲区里的东西“吐”出来**发给屏幕。所以你直接运行 `./a` 看到的是 6 个。
- **输出到管道/文件（非互动模式）：** 采用 **全缓冲 (Fully Buffered)**。**即便有 `\n`，它也不会立刻刷新，而是等缓冲区满了或者程序结束时才发送。**

### 2. 状态机的视角分析

让我们看看当你运行 `./a | cat` 时，缓冲区是如何随着 `fork()` 复制的：

#### **第一轮循环 ($i=0$)：**

1. **P1** 执行 `printf("Hello\n")`。因为是**全缓冲**，`"Hello\n"` **留在了 P1 的缓冲区里**，没发给 `cat`。
2. 此时**有 1 个 `Hello` 在缓冲区**。

#### **第二轮循环 ($i=1$)：**

1. **P1 执行 `fork()`**：分裂出 **P3**。
	- **关键点：** **`fork` 会复制整个内存空间，包括缓冲区。**
	- 此时 P1 和 P3 的缓冲区里**都各有一个**来自 $i=0$ 的 `"Hello\n"`。
2. **P2 执行 `fork()`**：分裂出 **P4**。
	- 同理，P2 和 P4 的缓冲区里也都各有一个来自 $i=0$ 的 `"Hello\n"`。
3. **四进程打印**：**P1, P2, P3, P4 各自在自己的缓冲区里又存入了一个 `"Hello\n"`**。
4. 此时，这 **4 个进程的缓冲区里各有两个 `Hello`。**

#### **程序结束：**

当这 4 个进程**执行完毕退出时，系统会自动冲刷（Flush）**它们的缓冲区。

- $4 \text{ 进程} \times 2 \text{ 个 Hello/进程} = 8 \text{ 个 Hello}$。

------

### 3. 如何验证这个理论？

如果你想在 `| cat` 的情况下依然只看到 6 个，你只需要在 `fork()` 之前强制清空缓冲区：

```c
for (int i = 0; i < 2; i++) {
    fflush(stdout); // 每次 fork 前手动把缓冲区里的东西“吐”干净
    fork();
    printf("Hello\n");
}
```

**加了 `fflush` 之后，父进程缓冲区里的 `Hello` 已经发给了内核，子进程分裂出来时缓冲区就是空的**，这样你就只会得到 6 个。

------

### 总结

这就是操作系统实验中非常经典的一课：**`fork()` 复制的是进程的完整状态，包括那些你肉眼看不见的库函数缓冲区。**

### 1. `CreateProcess`

用于创建一个新进程及其主线程。

```c

  LPCSTR                lpApplicationName,  // 可执行文件的路径
```

**理解 fork()**: fork() 会完整复制状态机；新创建的状态机返回值为 0，执行 fork() 的进程会返回子进程的进程号。同时，操作系统中的进程是并行执行的。程序的精确行为并不显然——model checker 可以帮助我们理解它。

在这个例子中，我们还发现执行 `./a.out` 打印的行数和 `./a.out | wc -l` 得到的行数不同。根据 “机器永远是对的” 的原则，我们可以通过提出假设 (libc **缓冲区影响**) 求证、对比 strace 系统调用序列等方式，最终理解背后的原因。标准输入输出的**缓冲控制可以通过 setbuf(3) 和 stdbuf(1) 实现。**

**理解 execve**: execve 有三个参数：**path, argv, envp**，分别是**可执行文件的路径**、**传递给 main 函数的参数**和**环境变量**。execve 是一个 **“底层” 的系统调用，**而 **POISX 额外提供了 execl 等库函数**便于我们使用。

## **进程替换（Process Replacement）**

如果说 `fork()` 是分裂状态机，那么 **`execve`** 就是**重置（Reset）并彻底改写状态机**。

------

### 1. 核心原理：夺舍 (Body Snatching)

`execve` 的作用不是创建一个新进程，而是**把当前进程的所有内容（代码、数据、堆栈）全部清空，然后加载一个新的程序来运行**。

- **进程 PID 不变**：就像一个人换了灵魂，**身体（PID）还是原来的**。
- **一去不回头**：**一旦 `execve` 成功，原程序中 `execve` 之后的代码永远不会被执行**。

------

### 2. 代码逐行详解

#### 1) 参数准备 (`argv`)

```
char *const argv[] = { "/bin/bash", "-c", "env", NULL };
```

这是传递给新程序的**命令行参数**。

- `argv[0]`：通常是**程序的路径**。
- `-c` 和 `env`：**告诉 bash 执行 `env` 命令（列出环境变量）**。
- **注意**：数组**必须以 `NULL` 结尾，这是 Linux 内核判断参数结束的标志**。

#### 2) 环境定义 (`envp`)

```
char *const envp[] = { "HELLO=WORLD", NULL };
```

这是**自定义的环境变量**。

- 通常进程会继承父进程的环境变量，但 `execve` **允许你开启一个“纯净”的环境。**
- 这里你只定义了一个变量：`HELLO=WORLD`。

#### 3) 关键调用 (`execve`)

```
execve(argv[0], argv, envp);
```

这是系统调用，参数含义如下：

1. **文件名**：要执行的二进制文件路径 (`/bin/bash`)。
2. **参数表**：传递给新程序的 `argv`。
3. **环境表**：传递给新程序的 `envp`。

#### 4) 错误处理

```
printf("Hello, World!\n");
```

这行代码在正常情况下**永远不会运行**。

- 如果 `execve` 成功，当前进程的代码**就被 `bash` 覆盖了**，这行 `printf` 已经从内存里消失了。
- 只有当 `execve` **失败**（比如找不到 `/bin/bash`）时，它才会返回并执行这一行。

------

### 3. 运行后的预期输出

当你运行这个程序，你会在终端看到类似：

```
HELLO=WORLD
PWD=/root/workspace/os2025/...
...（可能还有其他由 bash 自动生成的变量）
```

你会发现，你原本的 `printf("Hello, World!\n")` **没有输出**。

------

### 4. 从状态机视角理解

1. **初始状态**：状态机正在运行你的编译后的 C 程序。
2. **执行 `execve`**：内核接到请求，**把当前状态机的内存空间全部抹除**。
3. **加载新状态**：内核**把 `/bin/bash` 的代码读入内存**，将 **PC（程序计数器）指向 `bash` 的入口点**，并将 `envp` 放入其初始栈空间。
4. **继续运行**：状态机**从 `bash` 的第一条指令开始跑**，完全忘记了自己曾经是一个 C 程序。

### 总结

这就是为什么你在代码注释中看到 **"Reset the state machine"**。`execve` 是 Linux 中运行新程序的唯一真正方式（`system()` 和 `popen()` 底层都是先 `fork` 再 `exec`）。

## 5.3 总结

**Take-away Messages**: 操作系统通过进程抽象为应用程序提供了独立的执行环境。**进程是操作系统中最基本的资源分配单位**，它包含**程序本身**的状态和**操作系统内部**的状态。操作系统提供了**一系列系统调用 (如 Linux 中的 fork、exec、wait 和 exit，Windows 中的 CreateProcess 和TerminateProcess) 来创建、管理和终止进程。**

## 这个里面的ABI是什么意思

在底层系统编程中，**ABI (Application Binary Interface)** 翻译为“**应用二进制接口**”。

如果说 **API** 是程序员在**写代码时需要遵守的“合同”（源代码级）**，那么 **ABI** 就是**两个编译好的二进制文件之间通信的“握手协议”（二进制级）**。

结合你图片中的上下文，ABI 的核心意义在于规定了以下几点：

### 1. 数据的“长相” (Data Layout)

ABI 规定了**基本数据类型（如 `int`, `long`, `double`）到底占用多少个字节**，以及它们在**内存中是如何对齐**的。

- **例子**：在某些 ABI 中 `long` 是 4 字节，而在 Linux x86-64 的 ABI (System V ABI) 中 `long` 是 8 字节。

### 2. 调用约定 (Calling Convention) —— 最关键的部分

当你的程序调用 `execve` 或其他库函数时，ABI 规定了：

- **参数传递**：参数是**放在寄存器（如 `%rdi`, `%rsi`）**里，还是**压入栈（Stack）**里？
- **返回值**：函数执行完后，**结果放在哪个寄存器里（通常是 `%rax`）**？
- **栈帧布局**：**谁负责清理**栈空间？是调用者还是被调用者？

### 3. 为什么在 `execve` 这里很重要？

在你的代码里，你正在使用 `execve` 手动设置一个新的状态机。

- 当你调用 `execve` 时，你提供的 `argv` 数组和 `envp` 数组必须严格遵循系统的 ABI 规范**放在特定的内存位置**。
- 新程序（比如 `/bin/bash`）启动的第一秒，它会**根据 ABI 约定的规则去读取栈顶和寄存器，从而拿到你传给它的那些参数。**如果 ABI 不统一，`bash` 就会读到乱码。

### 4. ABI 与 API 的精简对比

| **维度**   | **API (Application Programming Interface)** | **ABI (Application Binary Interface)**     |
| ---------- | ------------------------------------------- | ------------------------------------------ |
| **阶段**   | **编译时**（写代码阶段）                    | **运行时**（程序**跑起来阶段**）           |
| **形式**   | 头文件 (`.h`)、函数名、参数名               | **寄存器、内存地址、二进制格式 (ELF)**     |
| **兼容性** | 只要代码能重新编译通过，API 就是兼容的      | 只要编译好的 `.o` 能直接跑，ABI 就是兼容的 |

### 形象比喻

- **API** 就像是**插头说明书**：告诉你要买三孔的插头。
- **ABI** 就像是**插座的物理规格**：规定了孔与孔之间到底是多少毫米，电压是多少。只有规格（ABI）对上了，你的电器（二进制程序）插上去才不会烧掉。

**所以，当你看到代码注释里提到状态机和 ABI 时，它其实是在提醒你：我们正在进行一种底层的、直接面对内存和寄存器的“接头工作”。**

## 6.2 进程的地址空间管理

### 进程的初始状态

- 只有**ELF 文件里声明的内存**和一些**操作系统分配的**内存
	- 任何其他指针的访问都是非法的
	- 如果我们从输入读一个 size，然后 malloc(size)
		- 内存从哪来呢？

### 一定有一个**系统调用**可以改变进程的地址空间

### 在状态机状态上增加/删除/修改一段可访问的内存

- MAP_ANONYMOUS: **匿名 (申请) 内存**
- fd: 把**文件 “搬到” 进程地址空间**中 (例子：加载器)

```c
// 映射
void *mmap(void *addr, size_t length, int prot, int flags,
           int fd, off_t offset);
int munmap(void *addr, size_t length);

// 修改映射权限
int mprotect(void *addr, size_t length, int prot);
```

### 1. `mmap`：建立映射

`mmap` 的作用是将一个**文件**或**设备**映射到**进程的虚拟地址空间。**映射成功后，你**可以像操作普通内存数组一样操作文件，而不需要频繁调用 `read` 或 `write`。**

**参数详解：**

- **`void \*addr`**：你想**把映射放在内存的哪个位置**。
	- 通常传 `NULL`，由**操作系统帮你选**一个合适的地方。
- **`size_t length`**：映射多大（字节）。
- **`int prot` (Protection)**：内存的**访问权限**（不能超过文件本身的打开权限）：
	- `PROT_READ`：可读。
	- `PROT_WRITE`：可写。
	- `PROT_EXEC`：可执行。
- **`int flags`**：**影响映射的特性**：
	- `MAP_SHARED`：对内存的修改会**同步到原始文件，且其他进程可见。**
	- `MAP_PRIVATE`：创建一个**“写时复制”（Copy-on-Write）的副本，修改不会影响原文件。**
	- `MAP_ANONYMOUS`：**不映射任何**文件（常用于实现自定义的 `malloc`）。
- **`int fd`**：文件的句柄。如果是**匿名映射，传 `-1`。**
- **`off_t offset`**：从文件的**哪个位置开始映射**（必须是内存**页大小**的整数倍，通常是 4KB）。

------

### 2. `munmap`：取消映射

当你用完了这块内存，需要告诉操作系统：“这块地址我不要了”。

- **`void \*addr`**：`mmap` **返回的那个起始地址。**
- **`size_t length`**：映射的大小。

> **注意**：如果不调用 `munmap`，这块虚拟内存会一直被占用，直到进程结束。

------

### 3. `mprotect`：修改权限

这是最酷的函数。它允许你在程序运行过程中，**动态地改变已经映射的内存页的权限。**

- **`void \*addr`**：起始地址（必须按**页对齐**）。
- **`size_t length`**：修改范围的大小。
- **`int prot`**：新的权限（如将 `PROT_READ | PROT_WRITE` 改为 `PROT_READ`）。

------

### 实际应用场景举例：JIT 编译器

想象你在写一个 Java 虚拟机（JVM）或 JavaScript 引擎：

1. 你先用 `mmap` 分配一块具有 `PROT_READ | PROT_WRITE` 权限的匿名内存。
2. 你在里面写入生成的机器码（这是“写”操作）。
3. 写完后，为了安全和执行，你调用 `mprotect` 将这块内存改为 `PROT_READ | PROT_EXEC`（可读可执行，但不可写）。
4. 然后你就可以跳到这个地址去执行代码了。

### 总结

这三个函数实质上是程序员与操作系统的**内存管理单元 (MMU)** 对话的接口：

- **`mmap`**：在页表里“占个座”，并**把座位和磁盘/内存关联**起来。
- **`munmap`**：把座位**“退掉”**。
- **`mprotect`**：修改**座位的“规则”**（比如不准乱动、只准看等）。

### Example 1: 申请大量内存空间

- 瞬间完成内存分配

	- libc 的大 malloc 会直接调用一次 mmap 实现

### Example 2: Everything is a file

- 映射大文件、只访问其中的一小部分

```c
with open('/dev/sda', 'rb') as fp:
    mm = mmap.mmap(fp.fileno(),
                   prot=mmap.PROT_READ, length=128 << 30)
    hexdump.hexdump(mm[:512])
```

### 1. 逐行深度拆解

#### `with open('/dev/sda', 'rb') as fp:`

- **`/dev/sda`**：这是 Linux 系统中第一块物理硬盘（通常是 SATA 或 SSD）的**设备文件**。
- **权限警告**：读取这个文件通常需要 **root 权限**（`sudo`）。如果你没有权限，这一行就会直接报错。
- **`'rb'`**：以二进制只读模式打开。

#### `mm = mmap.mmap(...)`

这一步是在将**物理磁盘的前 128GB** 映射到你进程的虚拟地址空间。

- **`fp.fileno()`**：获取磁盘设备的**文件描述符。**
- **`prot=mmap.PROT_READ`**：**设置内存权限**为“只读”。
- **`length=128 << 30`**：
	- `128 << 30` 等于 $128 \times 1024 \times 1024 \times 1024$。
	- 这表示你映射了 **128 GiB** 的空间。
	- **关键点**：这并**不会立刻消耗你 128GB 的物理内存（RAM）。它只是在虚拟内存里占了个位置**，只有当你**真正去读某一部分时，内核才会把磁盘数据加载到内存。**

#### `hexdump.hexdump(mm[:512])`

- **`mm[:512]`**：通过**切片操作**读取映射内存的前 512 字节。
- **这 512 字节是什么？** 这是**磁盘的第一个扇区（Sector 0）**。在传统的硬盘布局中，这就是 **MBR（主引导记录）** 所在的位置。
- **`hexdump`**：以**十六进制格式打印**出来，方便你查看二进制原始数据。

------

### 2. 这段代码在操作系统层面做了什么？

通常我们读取磁盘是这样的：

```
磁盘 -> 内核缓冲区 -> 用户缓冲区（Python 变量）
```

**使用了 `mmap` 后，过程变成了：**

```
磁盘 -> 内核缓冲区（与用户空间共享）
```

当你执行 `mm[:512]` 时，CPU 发现这块内存还没数据，触发一个**缺页异常（Page Fault）**，内核随后**直接把磁盘最开头的 512 字节载入，你的程序就能直接读取了**。

------

### 3. 你会看到什么输出？

如果你运行成功（且磁盘使用的是传统分区表），你会看到类似这样的十六进制内容：

- 开头可能是一些机器码（启动代码）。
- 中间会有分区表信息。
- **最后两个字节通常是 `55 aa`**（这是 MBR 的有效签名）。

------

### ⚠️ 极重要警告

1. **危险性**：如果你把 `PROT_READ` 改成 `PROT_WRITE` 并修改了 `mm` 的内容，你可能会**瞬间破坏掉你的分区表或文件系统**，导致电脑无法启动。
2. **WSL2/虚拟机环境**：如果你在 WSL2 里运行，`/dev/sda` 可能只是一个虚拟磁盘。
3. **NVMe 硬盘**：如果你的电脑使用的是 NVMe 硬盘，设备名通常是 `/dev/nvme0n1` 而不是 `/dev/sda`。

###  **Linux pmap 命令是用什么机制实现的？如果在 Windows 上实现同样的机制，应该怎么做？**

`pmap` 命令通过读取 `/proc/[pid]/maps` 和 `/proc/[pid]/smaps` 文件来获取**进程的内存映射信息**。Linux 内核将这些信息以**文本形式暴露在 `/proc` 文件系统中**，`pmap` 通过**解析这些文件实现功能，而无需直接调用特定的系统调用。**

在 Windows 上实现类似功能，可以使用 `VirtualQueryEx` 函数。该函数可以查询指定进程的虚拟地址空间信息，包括内存区域的类型、状态和保护属性等。结合 `ReadProcessMemory` 函数，可以进一步读取进程内存内容。通过遍历整个地址空间，可以实现类似于 `pmap` 的功能。

## 代码详解

```c
        // See: proc(5)
        string memfile = "/proc/" + to_string(pid) + "/mem";

        // We need root permission to open this file;
        // otherwise it would be too dangerous.
        fd = open(memfile.c_str(), O_RDWR);
        if (fd < 0) {
            perror(memfile.c_str());
            exit(1);
        }
```

- `string memfile = "/proc/" + to_string(pid) + "/mem";`
	构造**目标进程的 procfs 内存文件路径（`/proc/<pid>/mem`）**，该文件代表该进程的虚拟地址空间（见 `proc(5)`）。
- `fd = open(memfile.c_str(), O_RDWR);`
	**以读写 (`O_RDWR`) 模式**打开这个文件（`c_str()` 将 `std::string` 转为 C 字符串），返回的**文件描述符保存在 `fd`**。
- `if (fd < 0) { perror(memfile.c_str()); exit(1); }`
	若**打开失败**，使用 `perror` 打印带文件名的错误信息并以非零状态退出程序。
- 额外说明：**打开并写入 `/proc/<pid>/mem` 需要特权（通常为 root）**，因为直接读写别的进程内存是高危险的

## **在 Linux 下，除了修改 /proc/[pid]/mem，还有其他方式可以修改另一个进程的地址空间吗？假设我有权限。**

除了直接操作 `/proc/[pid]/mem` 外，还有以下方法可以修改其他进程的地址空间（需具备权限）：

1. **`ptrace` 系统调用**
	通过 `PTRACE_PEEKDATA` 和 `PTRACE_POKEDATA` 请求读写目标进程内存。调试工具（如 GDB）即依赖此机制，但需附加到目标进程（可能暂停其执行）。
2. **`process_vm_writev` 系统调用**
	允许**直接向目标进程写入数据**，效率高于 `ptrace`，且**无需暂停目标进程**。需要 `CAP_SYS_PTRACE` 能力或权限配置。
3. **动态库注入**
	通过 `ptrace` 或 `LD_PRELOAD` **向目标进程注入代码**，**间接修改**其内存（如调用 `mprotect` 修改权限后写入）。
4. **共享内存（需协作）**
	使用 `shm_open` 或 `mmap` **创建共享内存区域**，但需目标进程主动映射并配合访问。
5. **内核模块**
	编写自定义内核模块直接操作内存，但风险较高且需系统级权限。

**适用场景**：

- `ptrace` 适用于**调试或精细控制**；
- `process_vm_writev` 适合**高效批量写入**；
- 动态库注入常用于**逆向或热修复**。

## Linux 3.2 为什么会需要新引入 process_vm_writev 系统调用

`process_vm_writev` 是 Linux 系统调用，用于直接向目标进程的地址空间写入数据。其典型使用场景包括：

**适用场景：**

1. **高效进程间通信**：需要**跨进程批量传输数据**时（如共享内存的替代方案）
2. **动态热补丁**：**运行时修改**目标进程的代码/配置
3. **调试/监控工具**：**注入代码或修改内存状态进行调试**
4. **性能敏感操作**：**相比 `ptrace` 无需频繁暂停**目标进程，延迟更低

**复杂性来源：**

- 需要手动管理 `struct iovec` 数组，分别描述本地/远程内存布局
- 需处理跨进程地址空间映射（远程指针需在目标进程有效）
- 权限要求严格（需 `CAP_SYS_PTRACE` 或 root）

**对比 `ptrace`：**

- 优势：无暂停开销，吞吐量高
- 劣势：**不自动处理地址转换，错误处理更复杂**

适合对性能要求高且需精细控制内存操作的场景（如高频数据采集工具）。普通场景建议优先考虑更上层的 IPC 机制。

## 6.4 总结

**Take-away Messages**: 操作系统**通过虚拟内存为每个进程提供独立的地址空间**，实现了进程间的隔离和保护。操作系统通过 **mmap/munmap 实现地址空间的管理**，并且还**提供特定机制 (如 procfs、ptrace、process_vm_writev、共享内存等) 访问彼此的地址空间**。

# POSIX 实用程序参数语法要点总结

## 命令行语法基础

POSIX 标准**定义了命令行工具（实用程序）应该如何接收和处理参数**，这套规则让不同的命令有统一的使用方式，方便用户学习和使用。

## 命令行组成部分

一个典型的命令行包含**四个主要部分：**

- **命令名称**：如 `ls`、`grep`、`find` 等
- **选项**：以 `-` 开头的标志，如 `-a`、`-l`
- **选项参数**：**某些选项需要的额外信息**，如 `-f filename`
- **操作数**：命令**要处理的主要对象**，如文件名、目录名等

## 选项的使用规则

1. **短选项格式**：单个字母前加连字符，如 `-a`

2. **选项组合**：**多个不带参数的选项可以合并**，如 `-abc` 等同于 `-a -b -c`

3. 带参数选项

	：

	- 标准方式：`-f file.txt`（选项和参数分开）
	- 也允许：`-ffile.txt`（**选项和参数连在一起**）

4. **选项结束标记**：`--` 表示**选项部分结束，之后的内容都视为操作数**

## 实用技巧

1. **选项通常放在前面**：先写所有选项，再写操作数
2. **选项顺序一般不重要**：`ls -la` 和 `ls -al` **效果相同**
3. **特殊操作数 `-`**：在许多命令中，**单独的 `-` 表示使用标准输入/输出**
4. **数字参数**：默认按十进制整数处理

## 为什么这些规则很重要？

1. **一致性**：**所有命令遵循相似的模式**，容易记忆
2. **可预测性**：了解这些规则后，即使是第一次使用的命令也能猜出用法
3. **脚本编写**：编写脚本时可以依赖这些规则处理参数
4. **工具支持**：像 `getopt()` 这样的函数可以帮助程序员**轻松实现符合标准的参数处理**

## 实际例子

```bash
ls -la /home
grep -i "error" -n log.txt
find . -name "*.txt" -size +1M
```

这三个命令是 Linux 运维和开发中最常用的“组合拳”，分别用于**查看、搜索、定位**。

### 1. `ls -la /home` (查看目录详情)

- **作用**：列出 `/home` 目录下的所有文件和文件夹。
- **参数精解**：
	- `-l` (Long)：显示**详细信息（权限、所有者、大小、修改时间）**。
	- `-a` (All)：**显示所有**文件，包括以 `.` 开头的**隐藏文件**。
- **一句话总结**：**“事无巨细地查看用户目录里都有啥。”**

------

### 2. `grep -i "error" -n log.txt` (过滤关键词)

- **作用**：在 `log.txt` 文件中寻找包含 "error" 的行。
- **参数精解**：
	- `-i` (**Ignore case**)：**忽略大小写**（ERROR、Error 都能搜到）。
	- `-n` (**Number**)：**显示行号**，方便你直接去代码里定位。
- **一句话总结**：**“在日志里快速找出出错的位置。”**

------

### 3. `find . -name "*.txt" -size +1M` (高级搜索)

- **作用**：在**当前目录及其子目录**下，搜索大于 1MB 的所有 `.txt` 文件。
- **参数精解**：
	- `.`：表示从**当前目录**开始**递归向下查找。**
	- `-name "*.txt"`：按**文件名**匹配。
	- `-size +1M`：按**大小**过滤（**`+` 表示大于，`-` 表示小于**）。
- **一句话总结**：**“把占用空间的大文本文件全揪出来。”**

------

### 💡 进阶：如何把它们组合起来？

Linux 的魅力在于“管道” (`|`)。比如你想看日志里的错误，但日志太大，你可以： `find . -name "log.txt" -size +1M | xargs grep -i "error"` *(找到大于 1M 的日志，**然后在里面搜错误**)*

以下对 labyrinth 的一些具体解释：

1. **中括号扩起的参数是可选**参数。因此 `-m`, `-p`, `--move`, `--version` 都是可选的参数。
2. 同一个选项**可以有别名**。在 `labyrinth` 中，`-m` 和 `--map` 的含义是一样的，`-p` 和 `--player` 的含义是一样的。

**遵守 UNIX 对返回值的约定**

`main` 函数的**返回值代表了命令执行的状态**，其中 `EXIT_SUCCESS` 表示命令执行成功，`EXIT_FAILURE` 表示执行失败。**对于 POSIX 来说，0 代表成功，非 0 代表失败。**和以前的 Online Judge 编程不同，实际的系统必须**在输入不符合规约时及时处理**。

## 3. 正确性标准

### 3.1 地图文件规范

地图文件 (map.txt) 的格式如下：

- 若干行，每行包含相同数量的字符，代表迷宫地图
- 字符含义：
	- `#`：墙壁
	- `.`：空地
	- `0-9`：玩家 (数字代表玩家ID)
- 迷宫不超过 100 行、100 列
- 迷宫中**所有空地必须是连通的**，即从任意一个空地可以到达任意其他空地 (玩家视为空地)

### 3.2 基本命令

```bash
labyrinth --map map.txt --player id
labyrinth -m map.txt -p id
```

- 功能：解析地图，并打印 map.txt 中的内容 (原样打印)
- 参数：
	- `--map` 或 `-m`：指定地图文件路径
	- `--player` 或 `-p`：指定玩家ID（0-9）
	- `-m` 和 `-p` 可以互换位置
- 错误处理：
	- 如果地图文件不存在或格式不正确，退出并返回错误码 1
	- 如果玩家 ID 无效 (不在 0-9 范围内)，退出并返回错误码 1
	- 如果缺少任何必需参数，退出并返回错误码 1
	- 如果迷宫中的所有空地不连通，退出并返回错误码 1
	- 如果迷宫过大，退出并返回错误码 1

### 3.3 移动命令

```bash
labyrinth --map map.txt --player id --move direction
labyrinth -m map.txt -p id --move direction
```

- 功能：移动指定玩家
- 参数：
	- `--move`：移动方向，可选值为`up`、`down`、`left`、`right`
- 行为规则：
	- 只能移动到空地 (不能是墙壁或其他玩家所在位置)
	- 如果移动成功，退出并**返回错误码 0**
	- 果地图中没有该玩家记录，则将玩家放置在第一个空地（从上到下，从左到右查找第一个空地）
- 错误处理：
	- 如果移动失败 (目标位置是墙壁或其他玩家)，退出并返回错误码 1

### 3.4 版本信息命令

```bash
labyrinth --version
```

- 功能：显示版本信息
- 输出：必须包含 “Labyrinth Game”，其他信息可自定义
- 行为规则：
	- 如果命令行参数只有 `--version`，显示版本信息并返回错误码 0
- 错误处理：
	- 如果同时包含 `--version` 和其他参数，返回错误码 1

## 4. 游戏前端

为了让游戏更有趣，我们还为 `labyrinth` 提供了两种不同的前端实现方式，让玩家可以更直观地体验游戏：

- 🎮 本地双人对战：两名玩家使用不同的按键 (WASD/HJKL) 在同一个终端窗口中控制各自的角色。前端程序会自动调用 `labyrinth` 命令行工具来更新游戏状态，并在每次移动后刷新屏幕显示最新的迷宫状态。
- 🌐 网络多人对战：在这种模式下，服务器会为每个 ssh 连接的玩家自动分配 ID，每个玩家可以看到所有其他玩家在迷宫中的位置。服务器会序列化和处理所有玩家的移动请求，确保游戏状态的一致性。

前后端分离的架构设计是现代软件开发中常用的一种模式：后端核心游戏逻辑和状态管理。它提供标准化的命令行接口，处理地图加载、玩家移动验证、游戏状态更新等核心功能，而不关心游戏如何展示给用户。前端则包括本地双人和网络多人界面，负责用户交互和游戏展示。它调用后端命令处理游戏逻辑，将游戏状态以直观方式呈现给玩家，并处理用户输入转换为对后端的调用。

前后端架构带来了关注点分离，后端专注于逻辑的正确性，前端专注于用户体验；其次是灵活性，可以轻松开发不同的前端界面而无需修改核心逻辑；最后是可测试性，可以独立测试后端逻辑，确保其正确性。
